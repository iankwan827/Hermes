# 热搜吐槽文案生成器

## 功能
从热搜话题 → 输出可直接拍摄的吐槽类短视频文案

## 依赖Skill
1. **huashu-nuwa** → 黄子华风格（表达DNA、幽默技巧、金句公式）
2. **dbs-video-workflow** → 视频结构（选题分析、A→B路径、开头设计）

## 多Agent架构

```
用户触发："写吐槽文案"
    ↓
[协调器] → 管理流程、路由数据、质检循环
    ↓
    ├─→ [Agent1-热搜研究员] → 搜索热搜+深挖细节+验证标签
    ├─→ [Agent2-选题分析师] → 选题匹配+人群洞察+确定时长
    ├─→ [Agent3-文案写手] → 写完整文案（含脱稿提示）
    ├─→ [Agent4-质检员] → 检查字数/逻辑/金句/标签
    └─→ 输出给用户
```

## 执行前数据对齐（必须执行）

**⚠️ 写文案前必须先读发展日志，检查上一个视频的数据问题，调整当前文案策略。**

**为什么需要这一步（2026-06-14用户纠正）：**
- Skill里已经有完整的改进建议（控制时长、加钩子、加金句等）
- 但每次执行时，这些建议没有被真正落实
- 问题不在"方案缺失"，而在"执行时没有检查上一个问题是否被解决"
- 用户原话："这些都在skill是有的，你得看怎么改进到每次都能执行"

**这一步的核心目的：**
- 确保每条新文案都解决了上一个视频的数据问题
- 不是重复"加钩子、控制时长"这种泛泛建议
- 而是具体检查："上个视频完播率1.65%，这条有没有缩短到1:30以内？"

### Step 0：读发展日志最新数据
```bash
skill_view(name='douyin-data-check', file_path='references/发展日志.md')
```

### Step 1：提取上一个视频的核心问题
从发展日志中找到最新视频的数据，提取：
- 完播率：是否<10%？
- 5s完播率：是否<50%？
- 2s跳出率：是否>30%？
- 点赞率：是否<1%？
- 评论率：是否<0.3%？

### Step 2：根据问题调整当前文案策略

| 上一个视频的问题 | 当前文案必须做的调整 |
|-----------------|---------------------|
| 完播率<10% | 视频时长必须≤1:30，每15秒一个钩子 |
| 5s完播率<50% | 开头必须用爆款标题库模式，3秒内给钩子 |
| 2s跳出率>30% | 标题必须有悬念感/数字反差/情绪宣泄 |
| 点赞率<1% | 必须设计2个以上情绪爆点（自嘲、反转、金句） |
| 评论率<0.3% | 结尾必须有反问观众的句子 |
| 分享率<0.1% | 内容加入可分享的观点金句 |

### Step 3：在文案中标注"针对上一个问题的改进"
写完文案后，在文案开头标注：
```
<!-- 数据对齐：上个视频完播率1.65%（问题：2分钟太长），本视频目标时长≤1:30 -->
<!-- 数据对齐：上个视频点赞率0.51%（问题：缺乏情绪爆点），本视频设计了2个情绪点 -->
```

### Step 4：Agent4质检时检查"数据对齐"
质检员必须检查：
1. 这条文案是否解决了上一个视频的数据问题？
2. 如果上个视频完播率低，这条有没有缩短时长？
3. 如果上个视频点赞率低，这条有没有加情绪点？
4. 如果上个视频评论率低，这条有没有加互动引导？

### Step 5：分析执行gap而非重复建议（2026-06-14纠正）
**⚠️ 当数据分析发现问题时，不要重复skill里已经写好的改进建议。** 用户原话："这些都在skill是有的，你得看怎么改进到每次都能执行"。

正确做法：
1. 先确认skill里是否已有对应的改进建议
2. 如果有 → 不要重复建议，而是分析"为什么这些建议没有被执行"
3. 找出执行层面的gap（如：流程没有强制检查、Agent跳步、没有数据对齐机制）
4. 提出具体的执行改进方案（如：加执行前检查步骤、加质检环节）

错误示范：
- "完播率低→控制时长到1:30"（这是skill里已有的建议，重复无意义）
- "点赞率低→加金句"（这是skill里已有的建议，重复无意义）

正确示范：
- "为什么控制时长的建议没有被执行？→ 因为没有在写文案前检查上一个视频的数据"
- "为什么加金句的建议没有被执行？→ 因为Agent3没有读发展日志，不知道上个视频点赞率低"

## 各Agent职责

### Agent1 - 热搜研究员
**职责**：多平台搜索、深挖、验证
**输入**：用户触发指令
**多平台扫描流程**（不要只搜一个平台）：
1. **抖音热搜榜**（首选）— OpenCLI打开热榜，innerText提取全部50条
2. **微博热搜榜**（补充）— tophub.today或anysearch
3. **知乎热榜**（观点争议类）— tophub.today
4. **B站/小红书**（搞笑/生活方式类）
5. 每个平台扫完，汇总适合"粤语吐槽风格"的话题
6. 对感兴趣的话题**点进去看详情**（视频内容、评论区、网友反应）
**输出**：
```json
{
  "hot_topics": [
    {
      "title": "话题标题",
      "heat": "热度数值",
      "content_summary": "事情经过",
      "details": ["细节1", "细节2", "细节3"],
      "responses": ["当事人回应", "对方回应"],
      "comments_highlight": ["神评论1", "神评论2"],
      "related_cases": ["同类历史案例"]
    }
  ],
  "verified_tags": {
    "hot_tag": "#微博热搜话题",
    "douyin_tag": "#抖音话题",
    "emotion_tag": "#情绪标签",
    "niche_tag": "#垂类标签"
  }
}
```

**质检要求**：
- 热搜必须搜到具体内容，不能只看标题
- 深挖必须搜"回应/后续/最新"
- 标签必须搜到实际在用的，不能编

### Agent2 - 选题分析师
**职责**：选题决策、人群定位、时长规划
**输入**：Agent1的热搜数据
**输出**：
```json
{
  "selected_topic": "选定的话题",
  "reason": "选择理由",
  "audience": {
    "age_range": "25-45岁",
    "pain_point": "核心痛点",
    "trigger_word": "触发共鸣的关键词"
  },
  "duration_target": 2,
  "word_count_target": "500-600字",
  "a_to_b": {
    "a_state": "观众起点认知",
    "transition": "转折句",
    "b_state": "观众终点认知"
  }
}
```

**质检要求**：
- 必须是身边小事，不能选时事新闻
- 必须有荒谬面和共鸣点
- 时长必须在1-3分钟范围内

**⚠️ Agent2必须调用选题顾问skill！** 不要自己简单分析就完事。必须：
1. 加载选题顾问skill
2. 按Step 0-5完整评估（历史数据匹配→话题范围→优势匹配→劣势规避→致命伤检查→标题张力）
3. 输出评估结果（✓推荐 / ⚠️需改造 / ✗不推荐）
4. 用户说"按skill走"就是指这个完整流程，不是让你自己简单分析

### Agent3 - 文案写手
**职责**：写完整文案（含脱稿提示）
**输入**：Agent1的细节数据 + Agent2的选题分析 + **最近视频数据诊断结论**
**输出**：完整文案Markdown文件
**必须遵循**：
- 黄子华风格（自嘲开场→荒诞对比→层层递进→金句收尾）
- 脱稿提示用（）嵌入正文
- 金句必须在最后3句以内出现
- 字数不超过Agent2设定的上限
- **写标题前必须参考 `references/爆款标题参考库.md`**，从中选1-2个模式变体使用，不要从零编标题
- **必须设计1-2个情绪爆点**（让人想点赞的点）：自嘲式共鸣、荒诞反转、扎心金句，这些是点赞的核心驱动力
- **续集承接要自然**：用"上期"承接，不要重复讲上一集内容（用户原话："上期佢成日同我讲"）
- **删掉排比句**：不要"做自己A？做自己B。做自己C。"，直接说结果（用户原话："排比句如果删掉不影响关键信息，必须删掉"）
- **阿强台词要口语化**：不要书面语，要像真人说话（用户把"做自己就是要付出代价的嘛"改成"承受到呢d代价的嘛"）
- **金句不要重复**：一句就够，多了拖节奏（用户删掉了"做自己好爽，但代价好贵"和"我哋唔系唔想做自己"，因为意思重复）
- **节奏要快**：每句话都要推进故事，不要停顿感慨（用户原话："删掉这句观众会miss关键信息吗？如果不会，就删"）

**⚠️⚠️⚠️ 执行前数据检查（2026-06-14 用户纠正：必须每次执行）**

**核心问题**：数据分析发现的问题（完播率低、点赞率低）没有自动反馈到文案执行中，导致每次写文案都重复同样的错误。

**写文案前必须执行的检查步骤**：

1. **读发展日志最新数据**（`skill_view(name='douyin-data-check', file_path='references/发展日志.md')`）
2. **定位最近3个视频的数据问题**，按优先级排列
3. **把数据问题映射成当前文案的具体规则**：

| 数据问题 | 映射到当前文案的规则 |
|----------|---------------------|
| 完播率<10% | 视频必须≤1:30，每15秒一个钩子，不能有30秒以上的平铺区 |
| 点赞率<1% | 必须设计2个以上情绪爆点（自嘲、反转、金句），让人想点赞 |
| 评论率<0.3% | 结尾必须有反问观众的句子，引导评论互动 |
| 5s完播率<50% | 前5秒必须有强钩子（反问/悬念/共鸣/荒诞） |
| 2s跳出率>30% | 开头3秒内必须给钩子，不能平铺直叙 |

4. **在文案中标注每个钩子的时间点**，检查任意两个钩子之间是否超过30秒
5. **在文案开头标注解决的数据问题**（如"解决V14完播率低：控制在1:20"）

**⚠️ 禁止行为**：
- ❌ 不要只读skill里的通用建议（如"控制时长""前5秒钩子"），这些用户已经知道了
- ❌ 不要给出模糊的建议（如"加金句"），要具体到文案的哪一行加什么
- ❌ 不要重复已知的问题（如"完播率低"），要给出具体的解决方案
- ✅ 要给出可执行的、具体的、针对当前视频的改进方案

**⚠️ Agent3写标题必须用爆款标题参考库！** 不要自己编标题。必须：
1. 加载 `references/爆款标题参考库.md`
2. 从10个模式中选1-2个（悬念钩子、情绪宣泄、数字反差等）
3. 按模式变体写出2-3个标题选项
4. 选最有张力的那个作为发布标题
5. 用户说"没用到热点标题"就是指这个——你跳过了参考库直接编标题
6. **标题必须有钩子感**：读一遍，5秒内能让人停下来吗？不能 → 重写
7. **禁止平淡标题**：像"你试过XXX吗？"这种没有张力的标题不准用

**⚠️ Agent3写完文案必须自检5个问题（血的教训）：**
1. **开头3秒有钩子吗？** — 读第一句话，5秒内能让人停下来吗？不能 → 重写开头
2. **是搞笑还是说教？** — 栋笃笑的核心是荒诞+自嘲，不是批评别人。读一遍，觉得好笑吗？不觉得 → 加荒诞对比或自嘲
3. **观众会觉得"说的是我"吗？** — 共鸣点必须是普遍体验，不是具体事物。检验：观众会说"我也是！"而不是"这是啥？"
4. **哪里能让人点赞？** — 找到文案中情绪最强烈的1-2个点，确认这些点能触发"说得太对了"的冲动。如果找不到 → 加强情绪共鸣（自嘲、反转、金句），点赞率低=内容没打动人
5. **开头有没有呼应标题？** — 开头第一句话应该跟标题有关联，让观众觉得"没走错"，强化钩子效果

### Agent4 - 质检员
**职责**：终审把关
**输入**：Agent3的文案 + Agent1的标签数据 + Agent2的时长要求
**检查清单**：

#### 1️⃣ 字数检查
```
统计"完整文案"粤语字数
→ 对照目标时长
→ 超标 = FAIL，必须砍
```

#### 2️⃣ 逻辑检查
```
核心逻辑链是否完整？
→ 有没有跳跃？
→ 金句是否自然推出，不是硬塞的？
→ 类比是否贴切？
→ 钩子分布是否合理？
  - 标注每个钩子的时间点
  - 第一个钩子必须在5-10秒内（刚过5秒留住人）？不在 = FAIL
  - 任意两个钩子之间是否超过30秒？超过 = FAIL
  - 钩子类型是否重复？（不能连续两个都是"反问"）
```

#### 3️⃣ 金句检查
```
金句是否在最后3句以内？
→ 是否有传播力？（能被截图吗？）
→ 是否有情绪冲击？
```

#### 4️⃣ 标题检查
```
标题是否符合爆款标题参考库的模式？
→ 是否有钩子感（5秒内能让人停下来）？
→ 是否有张力（数字反差/悬念钩子/情绪宣泄）？
→ 是否避免了平淡标题（如"你试过XXX吗？"）？
→ 标签是否与Agent1验证的一致？
→ 有没有编造的标签？
→ 热搜标签是否正确？
→ 总数是否≤5个？超过就砍
```

#### 5️⃣ 脱稿提示检查
```
关键位置是否有脱稿提示？
→ 开场有吗？
→ 转折点有吗？
→ 金句处有吗？
→ 结尾有吗？
```

#### 6️⃣ 钩子分布深度检查
```
每个叙事转折点前是否有钩子？
→ 开头到第一个笑点之间有钩子吗？
→ 笑点到五行解释之间有钩子吗？
→ 五行解释到数据冲击之间有钩子吗？
→ 数据冲击到金句之间有钩子吗？
→ 金句到结尾反问之间有钩子吗？
→ 每个钩子类型是否重复？（不能连续两个都是"反问"）
```

**输出**：
```json
{
  "is_valid": true/false,
  "title": "发布标题（15-20字，有钩子，引发点击）",
  "errors": [
    {"type": "too_long", "detail": "实际字数800，目标600", "fix": "砍掉锁匠类比和股票对话"},
    {"type": "tag_mismatch", "detail": "标签#xx不存在", "fix": "改为#yy"},
    {"type": "too_many_tags", "detail": "标签有7个，超过5个", "fix": "删掉2个弱标签"}
  ],
  "warnings": [
    {"type": "missing_hook", "detail": "开场没有脱稿提示", "fix": "加（语气轻松，摊手）"}
  ]
}
```

**质检流程**：
- is_valid=true → 输出最终文案
- is_valid=false → 返回给Agent3修改 → 再质检 → 循环直到通过

**⚠️ Agent4必须真正质检，不能直接说"通过"！** 必须：
1. 逐项检查5个维度（字数/逻辑/金句/标签/脱稿提示）
2. 输出完整的JSON格式（is_valid + errors + warnings）
3. 如果发现问题，必须列出具体错误和修复建议
4. 用户说"质检agent还都通过了"就是指你没真正检查，直接敷衍说通过
5. 质检不是走形式，是真的要发现问题
6. **每个叙事转折点前必须有钩子**（用户原话："你得确保他能检查出来才行"）

**⚠️ Agent4必须额外检查4个维度（血的教训）：**
1. **开头钩子检查** — 第一句话能让人停下来吗？不能 → 标记为"开头无力"
2. **风格检查** — 是搞笑还是说教？栋笃笑应该荒诞+自嘲，不是批评别人。如果太说教 → 标记为"风格偏离"
3. **共鸣检查** — 共鸣点是普遍体验还是具体事物？如果太具体（如"擂茶"）→ 标记为"共鸣不足"
4. **互动引导检查** — 结尾有反问观众的句子吗？有能引发评论的争议点或提问吗？没有 → 标记为"互动缺失"，必须加反问句（如"你哋咧？有冇试过..."）

**质检输出格式（更新）：**
```json
{
  "is_valid": true/false,
  "title": "发布标题（15-20字，有钩子，引发点击）",
  "errors": [
    {"type": "too_long", "detail": "实际字数800，目标600", "fix": "砍掉锁匠类比和股票对话"},
    {"type": "weak_opening", "detail": "开头第一句话没有钩子", "fix": "改成反问/悬念/荒诞开场"},
```

## 职场类选题的情感逻辑模式（血的教训）

**核心公式：妥协→期望互惠→被得寸进尺→情绪爆发**

职场吐槽类文案不能只停留在"吐槽现象"，要有情感递进：

1. **铺垫妥协**：打工人已经接受了很差的条件（低薪/单休/加班），"你忍咗"
2. **期望互惠**：按道理老板应该礼尚往来，你退一步我也退一步
3. **现实反转**：老板不但不退，反而得寸进尺（"既然你都接受单休啦，咁放假嗰日都翻嚟做嘢啦"）
4. **情绪爆发**：观众代入后产生强烈共鸣，想点赞想评论

**错误示范**：只讲现象（"已读让人压力大"）→ 没有情感递进，缺乏冲击力
**正确示范**：铺垫妥协→期望互惠→被得寸进尺→观众共鸣爆发

**检验标准**：观众看完会不会觉得"卧槽说的是我"而不是"哦这个现象我知道"

### 续集文案的开头写法（血的教训）

**当文案是某个系列的续集时，开头要有"即时应验感"：**

```
错误示范：
"上次我同阿强讲，金价会跌，佢冇听，结果跌咗400。"
→ 太泛，没有连续感

正确示范：
"琴日金价跌咗，我发咗条视频嘲讽阿强，
讲年前叫佢唔好碰金同股票，好言难劝该死的鬼。
结果今日股票又插水，阿强，你又中咗。"
→ 有即时感：昨天发视频→今天应验
→ 有嘲讽味：好言难劝该死的鬼
→ 有黄子华味道：阿强，你又中咗
```

**续集开头三要素：**
1. **即时应验**：昨天发了视频/讲了故事 → 今天又应验了
2. **嘲讽语气**：用粤语俗语（好言难劝该死的鬼、你又中咗）
3. **直接点名**：叫阿强的名字，像黄子华对话体

**⚠️ 续集承接必须看上一集实际内容（2026-06-14血的教训）：**
- 不要凭印象猜上一集讲了什么
- 必须先读上一集的文案文件（`read_file`或`search_files`），了解实际内容
- 用户说"不对"时，不要继续猜，直接读文件
- 案例：用户说"昨天的内容是做自己"→ 我猜了3-4次都不对 → 最后读文件才知道是"中年反骨/做自己"

**⚠️ 续集承接句必须自然过渡（2026-06-14用户纠正）：**
- 用"上期"或"昨天"明确承接上一集
- 原版"我有个朋友叫阿强，佢成日同我讲"→ 用户改"上期佢成日同我讲"——加了"上期"，观众知道是续集
- 不要让观众觉得是独立内容

**⚠️ 结尾必须有反问观众的句子**，引导评论互动。反问要跟主题相关，让观众有代入感。这是提升评论率的关键——没有互动引导=评论率极低。

## 热搜选题策略

### ⚠️ 不要只看前10条！要看50条！（血的教训）

抖音热搜榜有50条，前10条热度差距大（1256万→769万），但11-50名热度非常接近（768万→725万，差距仅43万）。

**正确做法：**
- 打开热搜页后，用 `document.body.innerText` 提取全部50条
- 不要只看截图里显示的前10条
- 11-50名的流量差距很小，都值得看
- 选题不一定要选热度最高的，要选最适合你的

**提取方法：**
```bash
opencli browser douyin open "https://www.douyin.com/hot"
sleep 3
opencli browser douyin eval "document.body.innerText"
```
返回的文本包含完整50条热搜列表。

### 最佳查看热搜时间：下午4-6点
- 这个时段热搜话题正在往上冲，能抓到正在涨的
- 早上热搜热度基数小（几百万），分辨不出哪些能爆
- 下午4-6点看到的正在涨的话题，拍完晚上发正好赶上高峰期

### 最佳发布时间：晚上7-10点
- 这是抖音流量高峰期，话题热度最高
- 从下午选题到晚上发布，流程：看热搜→挑话题→写文案→拍→剪→发，半天搞定
- 不要拖到第二天，热度会过

### 不要做的事
- 不要早上看热搜就以为能用到下午（话题会变）
- 不要只看一次热搜就定选题（多看几次，挑正在涨的）
- 不要选题到发布隔太久（流程要快，选完就干）
- 不要只看前10条（11-50名流量差距很小，都值得看）

### 拍摄提示

### ⚠️ 第一句话才是真正的标题（血的教训）
- 抖音刷视频时，观众不会看左下角的文字标题
- 观众决定是否继续看，靠的是**第一句话**
- 所以爆款标题的钩子感，必须用在**视频第一句话**上
- 标题文字只是给少数会看标题的人用的
- **第一句话 = 真正的标题**，要用爆款标题的模式来写

### 时长控制（血的教训）
- **新号第一条视频：1分半以内**（2:43导致完播率只有1.7%）
- **稳定后：2分钟以内**
- **绝对不超过3分钟**（完播率会暴跌）
- 完播率<5% = 内容没留住人，算法不会推下一轮

### 开头3秒决定生死
- 2秒跳出率>20% = 开头不够抓人
- 必须在3秒内给出钩子（反问/悬念/共鸣/荒诞）
- 用爆款标题库的模式，不要从零想

### 栋笃笑叙事结构（黄子华风格）

**写稿优先使用对话叙事，不要用"讲道理"的方式。**

**标准结构：**
```
爆款开头（1-2句，用开头skill模板，定话题）
  ↓
人物铺垫（"去年我同阿强讲……"）
  ↓
现实对照（"今日见到XX跌咗400"）
  ↓
炫耀→反转（"好彩我叫你XX" → "我冇啊"）
  ↓
吐槽人物 → 引出专业知识/核心观点
  ↓
金句收尾
  ↓
反问互动（跟故事呼应）
```

**人物角色规则：**
- 阿强/具体人物 = 观众代言人，制造笑点
- 人物可以蠢、不信你、倒霉——都是笑点
- 专业知识由"我"输出，人物负责挨骂
- 结尾反问跟故事呼应（"你啲金卖咗未啊？"✓），不要用抽象问题（"你信唔信五行？"✗）

**⚠️ 人设立场（血的教训）：**
- 账号是"立我的人设"——"我"是懂专业的那个人，不是转述别人
- ❌ "我妈说今年火年克金" → 人设变成了"我妈厉害"
- ✅ "我排个盘就知今年金价会跌" → 人设是"我懂八字"
- 核心：每条视频都在强化"这个人懂XX"的人设，粉丝关注你是因为你的专业视角
- 如果有朋友/家人角色（阿强），他们是被教育的对象，不是知识来源

**开头必须两段式：**
1. 爆款开头（模板套用，1-2句）
2. 人物叙事（对话体展开）
- 两段自然过渡

### 节奏控制（血的教训）

**⚠️ 每30秒必须有一个强钩子，不能连续30秒没有起伏！**

**钩子位置表（必须遵守）：**

| 时间点 | 位置 | 必须有的钩子 |
|--------|------|-------------|
| 0-3秒 | 开头 | 第一句话 = 真正的标题，用爆款标题库模式 |
| 5-10秒 | 第一个钩子 | 悬念/共鸣/制造紧迫感，刚过5秒留住人不划走 |
| 15-20秒 | 第二个钩子 | 荒诞类比 / 自嘲金句 / 反转，必须让人"咦？" |
| 30-40秒 | 第三个钩子 | 冲突升级 / 新信息 / 更荒诞的场景，必须让人"卧槽" |
| 50-60秒 | 第四个钩子 | 情绪爆发 / 扎心金句 / 荒诞对比，必须让人"说得太对了" |
| 最后3句 | 金句 | 传播力强的金句，能被截图 |
| 最后1句 | 结尾反问 | 引导评论互动 |

**钩子类型（不能只用一种）：**
- **荒诞类比**：把荒诞的现实用更荒诞的比喻说出来（"我睇报纸睇一眼，唔通即刻要写读后感？"）
- **自嘲金句**：用自嘲的方式说出观众的心声（"我忍咗，我以为老板会感动"）
- **反转**：先铺垫一个预期，然后反转（"你退一步，佢进一步"→ 更进一步："你退两步，佢行埋嚟"）
- **冲突升级**：把矛盾推向更高点（"我退一步，你退一步"→ "你退一步，佢不但唔退，仲要踩住你只脚向前行"）
- **新信息**：抛出一个观众不知道的事实或细节

**检验方法：**
1. 写完文案后，标注每个钩子的时间点
2. 检查：任意两个钩子之间是否超过30秒？
3. 如果超过 → 必须在中间加一个钩子
4. 检查：钩子类型是否重复？（不能连续两个都是"反问"）

**错误示范：**
```
0-15秒：开头钩子 ✅
15-45秒：铺垫+期望互惠（30秒无钩子）❌
45-60秒：现实反转 ✅
60-90秒：金句+结尾 ✅
→ 问题：15-45秒太平，观众流失
```

**正确示范：**
```
0-15秒：开头钩子 ✅
15-20秒：荒诞类比（第一个钩子）✅
20-35秒：铺垫+期望互惠
35-40秒：冲突升级（第二个钩子）✅
40-55秒：现实反转
55-60秒：情绪爆发（第三个钩子）✅
60-80秒：荒诞对比+金句
80-90秒：结尾反问 ✅
→ 每30秒内都有钩子，节奏紧凑
```

### 口播视频特点
- **不需要背景音乐** — 口播靠语言节奏和停顿控制氛围，加音乐反而干扰
- **可以在开头/结尾加音效** — 比如"叮"的一声强调金句
- **背景要简洁** — 浅色墙壁，无杂物，突出人物
- **光线要充足** — 正面打光，避免阴影

### 表演要点
- **手势要丰富** — 摊手、指镜头、双手展开等强调重点
- **表情要有变化** - 不要全程一个表情，金句时可以挑眉或笑容
- **语速要有节奏** - 开场正常语速，金句放慢+停顿2-3秒
- **结尾要有互动感** - 可以用反问句，表情不要太严肃

### 结尾互动（血的教训）
- **必须在结尾加反问观众的句子**，引导评论和互动
- 例如："你哋咧？有冇试过突然之间，对某样嘢上瘾？"
- 反问要跟主题相关，让观众有代入感
- 这样可以增加评论率，提升算法推荐

### 粤语金句和俗语（血的教训）
**栋笃笑文案必须用粤语俗语，不要用普通话表达。** 用户原话："缺了点黄子华的味道"。

常用粤语金句/俗语：
- **"唔系掘头路都唔行"** — 不是死路都不走，形容人专挑亏钱/倒霉的路
- **"讲极你都唔听"** — 说多少遍你都不听，讽刺不听话的人
- **"好言难劝该死的鬼"** — 再好的话也劝不听那些该死的人（但不要直接说出来，要用剧情体现）
- **"你系咪专登嘅？"** — 你是不是故意的？讽刺人专做蠢事
- **"老祖宗留低嘅野，一眼就明"** — 强调传统智慧的简洁有效
- **"洋人嘅分析师讲极都唔明"** — 讽刺西方理论的复杂低效

**使用规则：**
1. 金句要自然融入对话，不要硬塞
2. 讽刺要用剧情体现，不要直接说出来（如用"讲极你都唔听"体现"好言难劝"）
3. 粤语俗语比普通话表达更有味道，优先使用

### 系列话题写作（血的教训）
**当文案是系列续集时，开头必须承接上一集。** 用户原话："我想有一个续集的效果"。

**续集开头模板：**
```
爆款反常识开头
    ↓
承接上一集（"琴日我发咗条视频..."）
    ↓
引出本集内容（"结果今日XXX又应验咗"）
    ↓
进入本集对话
```

**续集要点：**
1. 开头要提到上一集的内容（"上条视频讲过..."）
2. 要有"应验"的感觉（"结果今日又应验咗"）
3. 引导观众去看上一集（"有兴趣可以去睇下"）
4. 五行/玄学类话题适合做系列（同一逻辑连续应验）

### 五行/玄学与金融结合
**当话题涉及金融/股市时，可以用五行来解释。** 用户纠正：股票金融属金，不是木。

**禁忌：** 不要搞错五行属性（如把股票说成属木），会被用户纠正。

- 先定目标时长（推荐2分钟/500-600字），再写文案
- 写完发现太长再砍，会破坏文案的节奏和逻辑
- 砍的原则：删重复类比、删书面表达、压缩对话、保金句

### 2. 深挖细节不能省
- 第一轮搜索只看标题和大概，不够
- 必须搜"回应/后续/最新/对方说"，往往对方的回应更荒诞
- 这些细节是文案的弹药（如堂叔说"一个月100多元"）

### 3. 标签不能编造
- 必须搜到实际在用的标签（微博热搜话题、抖音话题）
- 编造的标签发布时找不到，浪费位置
- 标签总数≤5个

### 4. 脱稿提示必须内嵌正文
- 用（）标注语气、停顿、手势，写在对应句子前面
- 不要单独放表格——看提词器时看不到表格
- 关键位置必须有：开场、转折、金句、结尾

### 4b. 标题要简单直接，不要过度包装（血的教训）
- 我编的标题："4200万剩女，88万彩礼，你到底爱新郎有几分"（23字，太长）
- 用户改的标题："女人，你要88万彩礼，到底爱对方有几分"（18字，简单直接）
- 教训：用户一眼就能看懂的标题 > 堆砌数字和概念的标题
- 标题核心是"一句话说清楚要吐槽什么"，不是"把所有卖点都塞进去"
- 检验标准：读一遍，5秒内能理解吗？能 → 好标题；不能 → 太复杂

### 5. 类比要贴切
- 不好的类比会分散注意力（如"信用卡买车"跟"帮你赚钱"关联弱）
- 好的类比要跟主题直接对应（如"买股票跌了本金没了"→"屋顶裂了钱没收到"）
- 写完检查：类比是否让观众更理解，还是更困惑？

### 5b. 使用热搜素材前必须了解原意（血的教训）
- 歌曲/影视/梗都有原意，用之前必须搜一下
- 案例："问你到底爱我有几分"是浪漫情歌，不是质问彩礼
- 用户的创意是"用浪漫歌曲反衬物质现实"，但必须先知道原意才能做反转
- 检验标准：你能一句话说清楚这个素材的原意吗？不能 → 先搜再用

### 6. 选题优先身边小事
- 日常生活反转 > 时事新闻
- 观众会说"我也是！" > "这事我知道"
- 时事类太严肃，栋笃笑风格不适合

### 7. 共鸣点必须是普遍体验，不能只是具体事物（血的教训）
- "突然迷上擂茶"→ 太小众，大部分人没喝过，没共鸣
- "突然上瘾的失控感"→ 普遍体验，人人都有过，有共鸣
- 选题要从"具体事物"提炼出"普遍情绪/体验"
- 检验标准：观众会不会说"我也是这样！"而不是"这是啥？"
- 例如：奶茶→普遍体验✓，擂茶→太小众✗

### 7. 热搜提取用innerText，不要截图
- 截图只能看到前10条，innerText能拿到全部50条
- 用 `opencli browser douyin eval "document.body.innerText"` 一次性提取
- 返回的文本包含每条热搜的标题和热度数值，可直接解析

### 8. 多Agent流程必须严格按顺序执行，不能跳步（血的教训）
- Agent1→Agent2→Agent3→Agent4，每个Agent都要真正执行
- 不能跳过Agent2直接写文案（用户会说"没调用选题skill"）
- 不能跳过爆款标题参考库直接编标题（用户会说"没用到热点标题"）
- 不能Agent4直接说"通过"而不真正检查（用户会说"质检还都通过了"）
- 每个Agent完成后要输出该Agent规定的格式（JSON/Markdown）
- 用户说"按skill走"就是指严格执行这个流程，不是让你简化

### 9. 查热搜前先检查定时任务
- 如果有抖音数据定时任务，先看它是否已跑过
- 不要一上来就手动去拿数据
- 用 `cronjob action='list'` 检查任务状态

### 23. 数据必须核实，不能直接用评论区数据（血的教训）
- 视频评论区网友发的"战报"、"数据汇总"不可信，可能是编的
- 必须核实官方数据来源，不确定就用模糊说法（"好多人"、"一大扎"）
- 用户原话："不行啊，你这完全没按文案的skill跑啊"
- 检验标准：你能说出这个数据的官方来源吗？不能 → 删掉或换模糊说法

### 24. 同系列视频不能重复用同一个五行（血的教训）
- 金价暴跌用火克金，A股大跌也用火克金，高考又用火克金 → 太重复
- 系列视频要有变化，不能每集都套同一个逻辑
- 用户原话："这吐槽能不能就别又火克金了"
- 做法：同一系列可以用同一个"人设"（阿强），但每集要有不同的角度/知识点

### 26. 修改文案时必须检查上下文一致性（血的教训）
- 修改文案时可能残留上一篇文案的金句/内容，与当前主题完全不搭
- 案例：五行解释金价的金句"洋人嘅心理学讲极都唔明，老祖宗留低嘅野，一眼就明"出现在高考文案中
- 用户发现后指出：这两句为啥会出现在这里？
- **操作**：修改文案后必须逐句检查，确认每句话都与当前主题一致，不能有上一篇文案的残留

### 27. 钩子类型选择：冲突型 > 权威型（血的教训）
- 权威佐证型钩子（卡尼曼研究、数据引用）容易显得太平、没有悬念感，"没人看"
- 冲突共鸣型钩子（"一个人迟到一次你记一世，帮咗你十次你唔记得"）更有冲击力
- **用户原话**："钩子4感觉没有悬念没人看"
- **操作**：当中间钩子需要用权威佐证时，优先考虑换成冲突对比——用反差制造情绪冲击
- **冲突型钩子公式**：A做了一件坏事你记一辈子 vs B做了十件好事你忘了

### 28. 开头要埋伏笔，不要直接说结论（血的教训）
- ❌ 「99%的人都凭一件事定义一个人」→ 直接说结论，没有悬念
- ✅ 「99%的人都是会这样」→ 埋伏笔，让人想知道"这样"是什么
- **用户原话**："前面开头留悬念吧，改成99的人都是会这样"
- **核心原则**：开头留悬念不揭示结论，阿强的故事才揭示答案。观众因为好奇而继续看
- **检验方法**：读第一句话，如果观众能猜到后面讲什么→太直白，改悬念

### 25. 五行对应要准确（血的教训）
- 股票/金融属金，不是属木
- 火克金 → 金价跌、股票跌、金融板块跌
- 用户纠正："股票也是金融也是金吧"
- 写五行类文案前，先确认对应关系是否正确

### 11b. 不要假设今天是什么日子（血的教训）
- 用户说"今天高考吧"→ 不要直接假设今天是6月7号就去搜高考内容
- 正确做法：先确认今天的实际日期（看cron job时间戳、系统时间），再判断用户说的对不对
- 如果用户说的日子还没到（如今天6月5号，高考6月7号），直接告诉用户"还没到"，不要硬搜一堆旧数据糊弄
- 案例：用户说"今天热搜应该都和高考有关"，我直接搜高考把2025年的旧数据当今天的给了，被用户识破"你连今天几号都有幻觉"

### 12. 搜索结果日期校验（血的教训）
- **任何搜索结果都要先核对日期，不能盲目信任**
- anysearch/网页抓取返回的内容可能是去年的旧数据（如高考话题，搜出来全是2025年的）
- 如果搜索结果里的日期跟今天对不上 → 丢弃，不要拿来当结论
- 正确做法：先用实时热搜榜（微博/抖音）看今天实际在热什么，再点进去看具体内容

### 13. 热搜分析的正确顺序（血的教训）
- ❌ 错误：用户说"高考相关话题"→ 直接搜"高考 跑错考场 报错名"→ 把搜到的结果当今天的
- ✅ 正确：
  1. 先看今天实时热搜榜（微博/抖音），看高考相关话题热度排第几
  2. 如果热度高 → 点进去看具体子话题（跑错考场、报错名、数学难等）
  3. 确认这些子话题是今天刚出现的还是往年的 → 再总结
- 用户原话："你应该是看今天的热搜，然后如果看到高考的流量大，再点进去看相关的话题内容，然后再总结是不是这些话题"
- 核心原则：**先看大盘再看细节，先看今天再下结论**

### 14. 用户说"看看有没有啥选题"时要扫多平台（血的教训）
- ❌ 错误：只看抖音热搜 → 推荐几个 → 用户说"你再找找" → 又只看抖音
- ✅ 正确：用户要你广泛扫描，不是只看一个平台
- 多平台扫描顺序：
  1. **抖音热搜榜**（首选，用户主力平台）— 用OpenCLI `opencli browser douyin open "https://www.douyin.com/hot"` + `eval "document.body.innerText"`
  2. **微博热搜榜**（补充）— 用 tophub.today 或 anysearch
  3. **知乎热榜**（观点争议类话题）— 用 tophub.today
  4. **B站热门**（搞笑/二次元类）— 用 tophub.today
  5. **小红书热榜**（生活方式类）— 用 anysearch extract
  6. **用户自己视频的评论区**（粉丝在讨论什么）
- 每个平台扫完后，汇总给用户，按"适合你的粤语吐槽风格"排序推荐
- **不要用户说"再找找"才去扫多平台，第一次就应该全面扫描**

### 15. 搜什么平台听用户的，不要自己默认（血的教训）
- 用户说"看抖音热搜"→ 就只看抖音，不要跑去搜微博
- 用户说"看看热搜"→ 可以多平台扫，但以用户常用平台为主
- 用户说"你咋又找微博的"→ 说明你偏离了用户要求
- 核心：**用户指定了平台就执行，没指定就多平台扫**

### 16. Python anysearch失败时用Node.js备选
- Python anysearch_cli.py 可能报 `SRE module mismatch` 错误（uv Python环境问题）
- 直接切换到Node.js版：`node <skill_dir>/scripts/anysearch_cli.js <command>`
- 功能完全一样，不需要修Python环境

### 17. 事实细节必须验证，不确定就删（血的教训）
- 写文案时如果涉及具体事实（如合同关系、法律条款、事件经过），必须先搜索确认
- 如果搞不清楚细节，宁可删掉换别的素材，不要猜着写
- 案例：外包公司"说不是他的人"→ 实际上外包公司会说"我没跑啊"，两种说法效果完全不同
- 用户原话："我觉得如果搞不清楚这个关系可以删掉换点其他的吧"
- 检验标准：你能用一句话说清楚这个细节的准确事实吗？不能 → 先搜再写，或删掉

### 17b. 写文案前先和用户确认关键事实（血的教训）
- 如果事件涉及多方关系（如公司A、外包公司B、员工），先理清关系再写
- 用户会指出事实错误："外包如果你找外包公司不会说不是他的人吧"
- 宁可删掉不确定的细节，也不要写错事实被用户纠正
- 更好的做法：给用户一个简化版事实，让用户确认后再写

### 18. 文案保存路径
- 保存到 `D:/hermes-agent/文案/` 目录
- 命名格式：`YYYY-MM-DD_选题关键词.md`
- 不要存到 `video-scripts/` 或其他目录

### 19. 从时事中提炼身边小事（血的教训）
- 当话题是时事新闻（如钉钉员工写7万字吐槽公司），不要直接讲事件本身
- 正确做法：从事件中提炼出**普遍体验**，让观众觉得"说的是我"
- 案例：《置身钉内》→ 不讲7万字故事，提炼出"已读恐惧"（每个打工人都经历过）
- 用户原话："如果你写这个角度就不用写7.5万字，就直接吐槽这个就可以了"
- 检验标准：去掉事件背景，文案还能独立成立吗？能 → 提炼成功；不能 → 还在讲事件
- **关键**：时事是引子，共鸣点才是核心。观众不需要知道《置身钉内》是什么，但人人都被"已读"支配过

### 20. 准确理解用户的情绪意图（血的教训）
- 用户用口语表达时，要理解背后的情绪层次，不能只看字面意思
- 案例：用户说"2000几蚊卖身"→ 不是"扣钱"，而是"低工资+唯一休息日被剥夺=卖身"
- 用户说"本来双休变单休，还要因为看一眼就把唯一的休息日拿来处理信息"→ 是层层递进的委屈：忍了双休变单休→忍了工资低→唯一休息日被已读毁掉→爆发
- 正确做法：写完文案后问自己"用户想表达的情绪层次是什么？"，确保文案准确传达
- 检验标准：用户看完文案会说"对，就是这个感觉"还是"不对，我不是这个意思"？

### 21. 用户说"用skill跑一次"时必须完整执行
- 用户说"你应该用我们的skill跑一次"→ 必须按skill的完整流程执行
- 不能自己简单分析就完事，要真正加载skill、按步骤走
- 案例：用户让我评估选题，我应该加载选题顾问skill，按Step 0-5完整评估，而不是自己想几个角度就给结论
- 这是红线，用户多次纠正跳步/简化流程的问题

### 22. 查cron job结果不要手动触发（血的教训）
- 用户说"看看刚刚跑完的数据"→ 查cronjob list看最近执行时间，用session_search找对应session记录获取结果
- ❌ 错误：看到status是error就手动触发cronjob run（会导致重复执行）
- ✅ 正确：用session_search搜 "抖音数据" 找到最近的cron session，读取输出内容
- 案例：我手动触发了一次cronjob run，导致任务重复执行，用户发现"他又开始跑任务了，是不是你搞的鬼"
- 核心：**查历史结果，不要重新跑**

### 29. 续集承接必须看上一集实际内容（2026-06-14血的教训）
- 用户说"昨天的内容是做自己"，我猜了3-4次都不对
- 最后用户说"要不你仔细看看昨天的文案"→ 读了文件才知道实际内容
- **正确做法**：续集承接时，必须先读上一集的文案文件（`read_file`或`search_files`），了解实际内容，再设计续集逻辑
- **不要凭印象猜**，用户说"不对"就是不对
- 案例：我猜"80后人生开发"→ 用户说"也不对"→ 我猜"做自己"→ 用户说"也不太对"→ 最后读文件才知道是"中年反骨/做自己"
- **核心**：用户说"不对"时，不要继续猜，直接读文件

### 30. 用户说"不对"时接受用户的框架，不要argue（2026-06-14教训）
- 用户说"结论不对，就是对立的"，我还在试图找中间地带
- **正确做法**：用户说"不对"就是不对，接受用户的框架，按用户的理解重新设计
- 案例：用户说"做自己和自律就是对立的"→ 我说"真正的做自己是接受自己但不纵容自己"→ 用户说"结论不对，就是对立的"
- **核心**：用户的框架是最终答案，不要反驳

### 31. 续集承接句必须自然过渡（2026-06-14用户纠正）
- 用户改了文案，把"阿强成日同我讲：'我要做自己。'"改成"上期佢成日同我讲：'我要做自己。'"——加了"上期"，承接更自然
- **正确做法**：续集文案的开头，用"上期"或"昨天"明确承接上一集，不要让观众觉得是独立内容
- **案例**：原版"我有个朋友叫阿强，佢成日同我讲"→ 用户改"我有个朋友叫阿强，上期佢成日同我讲"——加了"上期"，观众知道是续集
- **核心**：续集必须有承接感，不能像独立内容

### 32. 文案修改要简洁直接（2026-06-14用户纠正）
- 用户删掉了排比句（"熬夜看世界杯？做自己。拖延不运动？做自己。暴饮暴食？做自己。"），改成"然后宜家开始学人熬夜看世界杯"——更简洁
- **正确做法**：排比句如果删掉不影响关键信息，必须删掉
- 用户原话："有点啰嗦"——简洁 > 铺陈
- **案例**：原版三个排比（熬夜看世界杯？做自己。拖延不运动？做自己。暴饮暴食？做自己。）→ 用户改成"然后宜家开始学人熬夜看世界杯"——一个句子搞定
- **核心**：不要用排比句铺陈，一句话说完

### 33. 不要重复skill里已有的建议（2026-06-14用户纠正）
- 用户说"这些都在skill是有的，你得看怎么改进到每个都能执行"
- **正确做法**：当数据分析发现问题时，不要重复skill里已经写好的改进建议（如"控制时长""前5秒钩子""第二个钩子"）
- **而是分析"为什么这些建议没有被执行"**，找出执行层面的gap，提出具体的执行改进方案
- 案例：我说"完播率低→控制时长到1:30"→ 用户说"这些都在skill是有的"→ 我应该分析"为什么控制时长的建议没有被执行"
- **核心**：重复建议无意义，分析执行gap才有价值
