# 八字软件开发调试经验

> 从实际开发和调试中总结的常见bug模式和解决方案。

## 一、五行相生相克映射（高频错误）

**必须用正确的映射：**

```javascript
// 相生：a生b
const shengMap = { '水':'木', '木':'火', '火':'土', '土':'金', '金':'水' };

// 相克：a克b
const keMap = { '木':'土', '土':'水', '水':'火', '火':'金', '金':'木' };
```

**常见错误：**
- 把相生写成"水':'金"（反了，应该是金生水）
- 把相克写成"木':'金"（反了，应该是金克木）

**验证方法：** 用甲木验证：
- shengMap['水'] = '木' → 水生木 ✓
- keMap['金'] = '木' → 金克木 ✓

## 三、得地判断（必须查所有四柱）

**正确逻辑：**
```javascript
// 得地：只要有一个地支在长生~帝旺范围就算
const changshengList = CHANGSHENG[dayWx];
let dediCount = 0;
for (let i = 0; i < 4; i++) {
  if (changshengList.includes(pillars[i].zhi)) dediCount++;
}
const dedi = dediCount >= 1;  // 有一个就算得地
```

**常见错误：**
- 只查日支，不查其他三柱
- 把"长生~帝旺"范围搞错（应该是前五位，不是前六位）

## 四、三得法实现顺序（关键）

**执行顺序：**
1. 先算三得法 → 存到全局变量 `sandeLevel`
2. 再算用神（`computeYongXiJi`）→ 使用 `sandeLevel` 判断身强身弱
3. 最后渲染UI

**常见错误：**
- `computeYongXiJi` 在 `renderTab2` 之前调用，但 `sandeLevel` 在 `renderTab2` 内部设置
- 导致用 `computeYongXiJi` 时 `sandeLevel` 还是空字符串

**解决方案：**
```javascript
// 在 doCalc() 中
computeSanDe(result);      // 先算三得法
computeYongXiJi(result.bodyStrength);  // 再算用神
renderTab2(result);         // 最后渲染
```

## 五、三会局 vs 交战（概念区分）

| 类型 | 含义 | 示例 | 力量变化 |
|------|------|------|---------|
| **三会局** | 三个相同五行汇聚 | 申酉戌三会金局 | 该五行力量大增 |
| **六冲** | 两个对立五行互克 | 卯酉冲 = 金木交战 | 双方力量都减弱 |

**关键区别：**
- 三会局是"成局"，不是"交战"
- 六冲才是"交战"
- 遇到三会局要考虑该五行是否太旺（病药用神）

## 六、正印格用食神泄秀（易错点）

**正印格可以用食神：**
- 正印 = 进货（学习积累）
- 食神 = 出货（才华输出）
- 正印用食 = 学以致用，经典高格局

**成格条件：**
1. 日主身强（印旺→身强）
2. 印食不贴身相克（印在年/月，食在时，中间隔日主）
3. 忌：强财破印、枭神夺食

**常见错误：** 以为正印格忌食神（错！正印格用食神是经典组合）

## 七、病不能补（易错点）

**规则：** 某五行是"病"（太旺）时，即使它理论上帮身（如印星），也不能用做用神。

**示例：** 金水旺的盘
- 水是印星 → 理论上帮身
- 但水是病的一部分 → 用水加重病情
- 所以水不能用做用神

**用神排序：** 木（泄水+耗金）> 火（克金）> 土（克水）

## 九、五行力量表角色映射（易错点）

**正确做法：** 用反向查找确定每个五行对日主的角色

```javascript
// shengMap: a生b → shengMap['水']='木' means水生木
// 要找"谁生日主"（印星），需要反向查找
const shengWx = Object.entries(shengMap).find(([k, v]) => v === dayWx)?.[0] || '';
// 要找"谁克日主"（官杀），需要反向查找
const keWx = Object.entries(keMap).find(([k, v]) => v === dayWx)?.[0] || '';
```

**常见错误：**
- 用 `shengMap[dayWx]` 得到的是"日主所生"（食伤），不是"生日主"（印星）
- 用 `keMap[dayWx]` 得到的是"日主所克"（财星），不是"克日主"（官杀）

**甲木示例：**
- shengMap['木'] = '火' → 这是食伤，不是印星
- 正确：shengMap中值为'木'的键 = '水' → 水是印星 ✓

## 十、病药逻辑（不要硬凑病）

**核心原则：** "没有病就是没有病"，不是每个盘都有病。

**正确流程：**
1. 先检查有无六冲交战 → 有则通关用神优先
2. 没有交战时，检查是否有**特定组合**的病（如金水旺、木火旺等）
3. 如果没有特定病象 → 显示"无明显病象"
4. 不要看到某行旺就说是病

**有病的情况示例：**
- 申酉戌三会金局 + 两个壬水 → 金水旺 = 病
- 寅卯辰三会木局 + 丙丁火多 → 木火旺 = 病

**没有病的情况示例：**
- 丁卯己酉甲子丁卯：没有三会金局（只有酉），水也不旺 → 无病

| 亥子丑月（冬） | 水 | 木 | 金 | 土 | 火 |

- 申酉戌月（秋）：木囚 → 不得令 ✗

## 十二、pi.hidden是对象数组（JS实现陷阱）

**排盘脚本输出的藏干是对象数组，不是字符串数组：**

```javascript
// 错误：pi.hidden = ['戊', '辛', '丁']
// 正确：pi.hidden = [{stem:"戊", god:"正财", type:"Main"}, {stem:"辛", god:"七杀", type:"Hidden"}, ...]

// 错误写法：
pi.hidden.forEach(h => { ganWx(h); }); // h是对象，不是字符串

// 正确写法：
pi.hidden.forEach(h => {
  const hStem = typeof h === 'string' ? h : (h.stem || '');
  ganWx(hStem);
});
```

**影响范围：** 所有需要读取藏干的地方（五行统计、得生判断、十神分析等）

## 十三、病药判断：用三得法判断所有五行

**核心原则：** 不是看到旺就是病，要用三得法判断每个五行的强弱。

**正确流程：**
```
对每个五行（金木水火土）：
  得令：月支对该五行是旺还是相？
  得地：该五行在四柱地支是否有长生~帝旺？
  得生：天干地支是否有生助该五行的？
  → 三得二以上=强，三得一或零=弱

找出强的（3/3）= 病
找药：强元素所生的五行，且该五行不是强 = 药（一石三鸟）
```

**示例（甲戌壬申乙酉壬午）：**
- 金：得令✓ + 得地✓ + 得生✓ = 3/3 = 强
- 水：得令✓ + 得地✓ + 得生✓ = 3/3 = 强
- 木：得令✗ + 得地✗ + 得生✓ = 1/3 = 弱
- 火：得令✗ + 得地✓ + 得生✓ = 2/3 = 中
- 土：得令✗ + 得地✓ + 得生✓ = 2/3 = 中

→ 病：金水旺（都3/3）
→ 药：木（水所生，不是强元素，泄水+耗金）

**注意：** 得地查的是每个五行对应的阳干，不是日主天干：
- 金 → 用庚查 CHANG_SHENG['庚']
- 木 → 用甲查 CHANG_SHENG['甲']
- 水 → 用壬查 CHANG_SHENG['壬']
- 火 → 用丙查 CHANG_SHENG['丙']
- 土 → 用戊查 CHANG_SHENG['戊']

## 十四、喜用神计算规则

**用神优先级：** 通关 > 病药 > 默认（格局/旺衰）

**喜用神对应关系（根据用神五行确定）：**

| 用神 | 喜神 | 忌神 | 仇神 |
|------|------|------|------|
| 木 | 火（克金，次选药） | 金（克木） | 水（病的一部分） |
| 水 | 木（泄金） | 土（克水） | 金（生水） |
| 金 | 土（生金） | 火（克金） | 木（被金克） |
| 火 | 木（生火） | 水（克火） | 土（被火生） |
| 土 | 火（生土） | 木（克土） | 金（被土生） |

**注意：** 用神=木时，喜神=火（不是水）。因为火可以克金（次选药），而水是病的一部分。

**身弱时的默认用神：**
- 用神 = 水（印星，生我）
- 喜神 = 木（比劫，同我）
- 忌神 = 金（官杀，克我）
- 仇神 = 土（财星，克印）

**身强时的默认用神：**
- 用神 = 金（官杀，克身）
- 喜神 = 土（财星，耗身）
- 忌神 = 水（印星，生身太过）
- 仇神 = 木（比劫，帮身太过）

## 十五、多Agent开发流程（八字软件）

**标准流程：** 架构师 → 开发 → 验收

**架构师任务：**
- 读需求文档和所有相关skill
- 设计模块清单（名称、对应skill、输入、输出）
- 规划实施顺序和依赖关系
- 输出实施方案

**开发任务：**
- 按实施方案逐个实现模块
- 每个模块必须有 analyze() 方法
- 必须读对应skill的SKILL.md获取分析逻辑
- 用测试案例验证

**验收任务（关键）：**
- 必须对照需求文档逐项检查
- 必须运行测试案例验证结果
- 必须检查每个模块的输出是否符合需求
- **不能只测"能不能跑"，要测"功能是否完整"**

**常见失败原因：**
- 架构师设计了架构，但没有明确告诉开发要实现哪些分析模块
- 开发只做了基础计算，没有按skill写分析逻辑
- 验收只测了排盘计算，没有检查分析模块

## 十六、空亡逻辑（必须按skill规则）

**核心规则：**
- **日柱空亡** = 检查年支/月支/时支是否出现在**各自旬首的空亡里**
- **年月时空亡** = 检查年支/月支/时支是否出现在**日柱的空亡里**（基于日柱的旬首）

**甲戌壬申乙酉壬午示例：**
```
年柱甲戌旬空亡：申、酉
月柱壬申旬空亡：戌、亥
日柱乙酉旬空亡：午、未
时柱壬午旬空亡：申、酉

日柱空亡检查（日支酉 vs 年月时空亡）：
  日支酉 → 年柱甲戌旬空亡申、酉 → 酉在 → 日柱空亡！
  日支酉 → 时柱壬午旬空亡申、酉 → 酉在 → 日柱空亡！

年月时空亡检查（年月时支 vs 日柱空亡）：
  时支午 → 日柱乙酉旬空亡午、未 → 午在 → 时柱空亡！
```

**常见错误：**
- 只检查日柱空亡，不检查其他柱的空亡
- 每柱各自算旬首，然后交叉检查（逻辑不对）

## 十七、变量管理：必须维护变量字典

**问题：** 多个函数共享变量时，经常出现"计算对了但显示错了"的问题。

**原因：**
1. 函数A计算了结果存到变量X
2. 函数B显示时重新计算，用了变量Y（不是X）
3. 显示结果和计算结果不一致

**解决方案：**
1. 维护`variable-dictionary.md`，记录每个变量的数据来源、赋值位置、使用位置
2. 共享变量必须在全局定义（不是函数内部）
3. 显示时直接用已计算的变量，不要重新计算

**变量字典模板：**
```
| 变量名 | 数据 | 数据来源 | 赋值位置 | 使用位置 |
|--------|------|---------|---------|---------|
| sandeLevel | 三得法结果 | computeSanDe() | line 477 | renderTab2, renderStrengthSummary |
| bingyaoMedicine | 病药用神五行 | renderYongShen() | line 1166 | renderYongShen, renderStrengthSummary |
```

## 十八、用户偏好：先问再改

**用户明确要求：** "你下次能不能先问了再改"

在修改八字分析逻辑或软件代码之前，应该先向用户确认修改方案，而不是直接修改。用户是八字命理专家，对分析逻辑有最终决定权。

**用户还要求：** "你能不能按需求来" — 必须严格按照需求文档实现，不能自己猜测逻辑。

**用户还要求：** "变量老不对" — JS变量作用域问题需要特别注意，全局变量要在使用前声明，函数间传递数据要用全局变量或参数。

**用户还要求：** "你能不能解决这个问题，好几次了。变量老不对" — 每次修改后必须验证变量是否正确传递，不能只改一个地方就认为修好了。
